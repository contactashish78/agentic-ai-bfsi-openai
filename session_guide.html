01Overview

This session follows one banking use case, a customer asking about their loan application, from a single LLM call up to a governed multi-agent system. Each module adds one capability, and the session ends with a working harness that combines the OpenAI API with approved business tools, reusable skills, guardrails and an audit trail.

Webinar objectives

  • Understand how the OpenAI API is used inside a BFSI application
  • Build a simple loan-service assistant
  • See how an AI application calls approved business tools
  • Understand the difference between single-agent and multi-agent systems

Learning outcomes

  • Use the OpenAI Python SDK (via aisuite) at a basic level
  • Send a BFSI request and process the response, including structured output
  • Explain how tool calling enables agent-like behaviour
  • Explain the role of single-agent and multi-agent architectures, and the governance controls BFSI needs

The journey

Key terms

LLM: the language model (here OpenAI gpt-4o-mini) that reads text and decides what to do
Tool: an approved function the application runs for the model, returning data or taking an action
Agent: a loop around the LLM that uses tools until the task is done or it must stop
Handoff: one agent passes the conversation to a specialist agent
Skill: a reviewed Markdown playbook the model reads; it says how to handle a request
Guardrail: deterministic code that checks input or output, outside the model

Prerequisites

  • Basic Python knowledge
  • Jupyter notebook or another Python development environment
  • OpenAI API access (an API key)
  • Basic familiarity with banking and loan processes

Why aisuite?

A thin, open-source wrapper over provider SDKs. The call shape is identical to the OpenAI SDK. The only change is the model string, "openai:gpt-4o-mini". It also turns plain Python functions into tool schemas, which keeps the demo code short and readable.

Module 1 · OpenAI SDK basics through a BFSI use case

  • Initialise the client: the raw OpenAI SDK first, then the identical call through aisuite
  • System and user instructions: the system prompt defines role, scope and rules (“cannot approve or reject loans”)
  • Pass a customer request, then extract and display choices[0].message.content and token usage

    model="openai:gpt-4o-mini",

The application becomes a Loan Service Agent: a loop around the model that can choose between answering directly or using a tool, review each result, decide whether to respond or escalate, and stop.

Module 4 · Multi-agent: conceptual extension

10 min · 04_multi_agent_and_harness

A single agent works well while it serves one domain. A real bank chat also gets questions about KYC, cards, fraud and collections. Putting all of those into one prompt with one big toolset makes the agent slower, harder to test and riskier, because every tool becomes reachable from every conversation. The multi-agent answer is to split the work: a front-desk agent that routes, and specialist agents that act.

Triage Agent

  • Job: understand the request and decide where it goes
  • Can: answer simple general FAQs, hand off to a specialist, point out-of-scope topics to the helpline
  • Cannot: look up accounts, raise tickets or give financial advice
  • Tools: only transfer_to_loan_service

Loan Service Agent

  • Job: loan status, missing documents, decision requests and complaints
  • Can: use the approved loan tools, load skills, escalate to a human
  • Cannot: approve, reject or change loans; handle non-loan topics (it hands those back with transfer_to_triage)
  • Tools: 4 loan tools, load_skill, transfer_to_triage

How a handoff works

  1. The Triage Agent reads the message and calls transfer_to_loan_service(reason="Status of LA-1001").
  2. The harness intercepts the call. No business logic runs; it records a handoff event in the audit log and switches the active agent.
  3. The next LLM call uses the Loan Service Agent’s system prompt and toolset. The full conversation, including the reason, carries over, so the customer never repeats themselves.
  4. The specialist finishes the task. If the customer changes topic, it hands back to triage. The per-turn step limit stops two agents from passing a request back and forth forever.
# harness/agent.py: two agents, one handoff each way
triage = AgentSpec(
    name="triage",
    instructions=TRIAGE_INSTRUCTIONS,
    tools=[],                          # routes only, no business tools
    handoffs=["loan_service"],         # harness generates transfer_to_loan_service
)
loan_service = AgentSpec(
    name="loan_service",
    instructions=LOAN_SERVICE_INSTRUCTIONS,
    tools=LOAN_TOOLS,                  # check_loan_status, get_missing_documents, ...
    use_skills=True,
    handoffs=["triage"],
)
harness = Harness([triage, loan_service], entry="triage")

Single agent vs multi-agent

Single agentMulti-agent (triage + specialists)
PromptOne prompt covers every domain and grows with each new oneSmall, focused prompts, one per domain
Tool accessEvery tool is reachable from every conversationLeast privilege: each agent sees only its own tools
Ownership & testingOne shared componentEach business team owns, tests and approves its own agent
Adding a domainEdit the shared prompt and re-test everythingAdd an agent and a handoff; existing agents are unchanged
Cost & latencyFewer LLM callsOne extra routing call per conversation
DebuggingOne traceMore moving parts, so the audit trail of handoffs is essential

Pattern used here: handoff

Control moves to the specialist, which talks to the customer directly. Simple, and a good fit when each request belongs to one domain.

Alternative: orchestrator

A manager agent calls specialists as tools and combines their answers. Useful when one request spans domains, e.g. “Where is my loan, and is my KYC complete?”
Lesson from rehearsal: an early version gave the Triage Agent the escalate_to_human tool. On complaints it escalated straight away, so the Loan Service Agent and its complaint playbook (acknowledge, check facts, confirm the ticket) never ran. Removing the tool from triage fixed it. Least privilege applies to routing agents too.
Takeaway: a handoff is just a tool call that the harness turns into a change of prompt and toolset. Start with one agent, and split when domains, owners or tool permissions diverge.

04Capstone: the BFSI agent harness

Module 5. Everything above, packaged with governance built in. The OpenAI API (via aisuite) is the reasoning engine. Everything the agent is allowed to do is controlled by deterministic code around it.

Tools vs skills: what’s the difference?

These two get confused because the agent loads a skill through a tool call (load_skill). The difference is in what comes back and how it is used.

The 📘 skill says what to do. The 🔧 tool does it.
🔧 Tool📘 Skill
What it isA Python function (code)A Markdown playbook (text)
Gives the agentData or an action: a loan’s status, a new ticketKnow-how: how to handle a type of request
Who runs itThe application executes itNothing executes; the text is added to the model’s context
Side effectsPossible (escalate_to_human creates a ticket)None
How the model finds itFull JSON schema sent with every callOnly name and one-line description in the prompt; full text loaded on demand
Who owns itDevelopers: code review and testsBusiness or compliance experts: content review
GovernanceAllow-list; every call auditedVersioned documents; every load audited
AnalogyThe bank systems a staff member may useThe SOP manual on their desk

What the harness contains

🔧 Approved tools

  • check_loan_status: read-only lookup
  • get_missing_documents: read-only lookup
  • get_document_checklist: read-only lookup
  • escalate_to_human: creates a ticket for a loan officer
  • load_skill, transfer_to_*: harness built-ins

No tool can approve, reject, waive or modify a loan.

📘 Skills (Markdown playbooks)

  • loan-status-explainer: plain-language meaning of each status
  • missing-documents: upload channel, formats, do’s and don’ts
  • complaint-handling: acknowledge, check facts, escalate, confirm ticket
  • decision-requests: politely decline, share status, offer escalation

Only names and descriptions sit in the prompt. Business and compliance teams can review and edit behaviour without touching code.

05BFSI governance summary

Prompts are guidance; code is enforcement. Each governance rule maps to a deterministic control in the harness.

Governance ruleHow the harness enforces itWhere
Use only approved toolsPer-agent allow-list. Any other tool call is blocked, returned to the model as an error and logged as a policy event.harness/agent.py
Do not allow agents to approve or reject loansNo such tool exists. A decision-request detector adds a policy reminder, and an output check replaces any “I approved / rejected…” reply with a safe message.harness/guardrails.py
Protect customer dataPAN, Aadhaar, card, phone, e-mail and account numbers are masked before text reaches the LLM or the log. Agents never ask for identifiers.harness/guardrails.py
Maintain human escalationAn escalate_to_human tool for complaints and disputes, plus automatic escalation when the step limit is reached.harness/tools.py
Record agent actions for auditEvery guardrail check, LLM call, tool call, skill load, handoff and escalation is appended to an audit log, already masked.logs/audit.jsonl
